jehlp-technical-writing

Markdown

Write or revise original jehlp.net explanations, instructions, help, interface text, and mathematical exposition with ASD-STE100 Issue 9. Preserve source, translated, literary, and formal content.

Read the owning repository's AGENTS.md and site-theme/docs/WRITING-STYLE.md. Locate site-theme beside the current repository, or resolve this skill's real path. Use the writing policy for all new original technical text and substantive prose edits. For a page that explains a mathematics result, also use jehlp-math-explainer.

Classify original prose and protected content before the edit. Preserve reader text, translations, quotations, names, citations, legal text, and code. Preserve NDB fictional dialogue, story text, bestiary prose, and item descriptions. Preserve data, formulas, formal statements, hypotheses, quantifiers, proof dependencies, and uncertainty.

Use short, complete sentences and consistent technical terms. Give instructions in the imperative, with prerequisite conditions first. Limit instructions to 20 words and descriptions to 25 words per sentence. Limit a paragraph to one topic and six sentences. Use active voice, simple verb forms, and no semicolons. Check dictionary meanings and parts of speech when the official dictionary is available. Retain precise mathematical and interface terms under the technical-term rules.

Edit the source of generated content. Rebuild affected pages, PDFs, exports, and indexes. Compare protected content with the original. Run the repository's tests. Obtain a separate technical-meaning review for mathematical proof edits. Report actual checks and any dictionary-review limit. Do not claim unsupported complete compliance.

jehlp-site-design

Markdown

Design or improve jehlp.net pages using the shared visual language while preserving each project’s reading, comparison, or working surface.

Read the owning repository's AGENTS.md and the theme's PHILOSOPHY.md and docs/DESIGN-SYSTEM.md. Locate site-theme beside the current repo, or resolve this skill's real path to its owning site-theme checkout.

Identify the primary task and choose the surface around it: reading, reference, collection, live monitor, chart exploration, or puzzle workspace. Put the real material or controls in the first useful viewport. Use the Readers reference: Georgia text and controls, bold Palatino headings, mono values, and sans only for tiny chart annotations. Retain paper/charcoal modes, restrained blue, square controls and quiet rules; do not impose a card grid or marketing hero.

Treat each project as an independent page with useful local navigation and source/download links. Retain the shared abstract Home emblem in the existing header beside the theme dial; do not add a fixed footer or new sticky bar. include it in authored/generator HTML for a no-JavaScript fallback. NDB Idle is exempt. For a masthead, use the shared identity contract in docs/COMPONENTS.md: a relevant transparent PNG from v2/marks as img.site-mark, 32px, empty alt—not Unicode or emoji. Keep identity separate from data colors.

Use margins for meaningful context and comparison; remove unexplained number gutters, oversized gaps and empty hero space. Remove duplicate headings, redundant controls in the same context and obvious instructions, but retain uncertainty, provenance, privacy boundaries and actionable state text. A puzzle's PNG-centered divider belongs at the start of its main puzzle unit, after complete rules and worked examples. Keep the unit's lead-in, solve links and grids together below it; identify the boundary by meaning, not the first image. Use the puzzle transition contract in docs/COMPONENTS.md for explicit exceptions and preserve all source content/order.

Give the puzzle transition a small ornament distinct from the masthead logo. When the grid and solve links feel detached, one thin, square-edged sheet may enclose the complete main unit, using the divider as its top edge. Keep examples outside and original diagram colors intact; avoid shadows and excess inset. Group only verified solver-only content into an action row, preserving post-grid links and notes in source order.

Inspect existing layout and CSS ownership before editing. Regular reading targets 1rem; navigation and controls .875rem; secondary metadata .75rem. These are design targets. Judge dense chart marks separately instead of shrinking all labels or changing board geometry. Ordinary single-choice selects adopt data-ui-select; retain richer grouped VN chapter browsers. Choose compact paginated rows with detail or an overflowing comparison matrix, not pagination plus an internally scrolling two-axis table.

Make a representative improvement, then extend only the proven pattern. Keep data, ranking, scientific interpretation, puzzle logic and bot policy outside a visual change. Record the actual reusable decision in site-theme/docs/DECISIONS.md and the shipped scope in docs/CHANGELOG.md. Use docs/QA-MATRIX.md to choose checks proportional to the change; do not report unperformed browser checks as passed.

Choose the smallest pattern that serves the material. Existing contracts cover directories, grouped fields, single-choice selects, segmented selections, responsive disclosures, section indexes, overflow regions, native dialog shells, copyable code and highlighted code listings (jehlp-code-highlighting). Edit authored templates before regenerating output. Publish new assets before their consumers. Check focus, keyboard, breakpoint transitions, empty/populated, and no-script behavior as relevant, plus existing consumer tests. jehlp-code-highlighting

Markdown

Show source code and structured data on jehlp.net pages with build-time syntax highlighting, the shared code palette and native disclosures.

Read the owning repository's AGENTS.md, the theme's PHILOSOPHY.md and the code contract in docs/COMPONENTS.md. Locate site-theme beside the current repository, or resolve this skill's real path to its owning site-theme checkout.

Highlight code during the build. Use highlight.js at a pinned version as a development dependency. Do not load a highlighter or a highlight.js theme in the browser. Choose the language from the file extension, and use plain text when the language is unknown. Highlighting adds spans only: compare the text content with the source after a change.

Use the shared markup: <pre class="ui-code" tabindex="0" aria-label="Source of name.py"><code class="hljs language-python">…</code></pre>. Load v2/components.css after base.css. The --code-* tokens in base.css follow the theme tones, so dark mode and print need no second palette. Do not add token backgrounds, line shading, bold keywords or a page-specific syntax theme. Long lines scroll inside the named code block. Use .ui-code--wrap for data whose values are prose, such as pretty-printed JSON notes.

Render one or two listings in the page. For a large collection, put each listing in a native details element with the file name in its summary. Generate one static fragment per listing and fetch it on the first open. Keep a plain-text source link in the closed panel, so the listing remains available without JavaScript. Link fragments for search only when their text is useful search content.

Format JSON with two-space indentation before you highlight it. Render Markdown and prose notes as prose, not as code. Add data-copy-code when readers will copy the listing. Do not reduce the type size to fit long lines.

Check both color modes, print, keyboard focus on the code block, a narrow screen and the largest listing. Record new adopters in docs/COMPONENTS.md.

jehlp-math-explainer

Markdown

Say what a mathematics result means on jehlp.net in a two-minute page, without its proof, for a smart reader without the background.

Read the owning repository's AGENTS.md, the theme's PHILOSOPHY.md and the math contract in docs/COMPONENTS.md. Locate site-theme beside the current repository, or resolve this skill's real path to its owning site-theme checkout.

Write the page

The reader asks one question: what does this statement mean? Answer it in two minutes, then stop. The reader is smart and curious, even without the background. Define each term once, in few words. Do not explain what the reader can infer. Do not show the proof.

Use a title and plain paragraphs, under 300 words. Do not add section headings, a summary under the title, status lines, history, a section on why the result matters, a section on what it does not say, or a source list. If a misreading is likely, correct it in one sentence where it arises. Link the source on the words that state the result. A landing page is a list of titles.

Use an example only if it shows an idea that the reader probably has not met. Give each page one figure or small table for the margin, and keep its caption short.

Check the facts

Short does not mean loose. Read the primary manuscript, not only its news coverage. News summaries can misread notation and scope. Take the statement and the bounds from the source. Name the people and the models that the source credits when the statement needs them.

Calculate each number on the page, and keep a short exact check in the repository's tests. State a claim as a claim: write "reports" until human experts confirm a result. Paraphrase sources.

Build the page

Add an explainer to the homepage repository as one entry in data/ai-math.json and one body in content/ai-math/<slug>.html. Write math between \( and \) or between \[ and \]. The build typesets it to native MathML with a pinned Temml. Do not load a typesetter in the browser. Do not put a formula in an image.

Load v2/components.css for the --math face and .ui-equation. Use .ui-math-char for a double-struck letter in a heading or other plain text. Put a formula that can overflow in .ui-equation with data-scroll-region, data-scroll-noun="of the formula" and an accessible name. Keep inline formulas short, and display a long one.

Use the same frame as the masthead. On a wide screen, put the text in one column and the figure in the margin beside it. On a narrow screen, keep the figure in the text flow. Calculate figures during the build as inline SVG on the theme tokens, with an accessible name.

Check both color modes, a narrow screen and 200% text. Run the owning repository's tests. A new explainer needs no new homepage entry, because the search crawl follows links from the landing page.

jehlp-data-ui

Markdown

Improve jehlp.net tables, filters, chart controls, and live status without changing the underlying data or domain logic.

Read the consumer's README, AGENTS.md, existing tests and relevant renderer before editing. Distinguish the stable data contract from presentation. Mystery-report ranking/export, profile scientific content, and dashboard state interpretation must remain intact during UI work.

Keep search/filter/sort controls together with results. Preserve reset, counts, access to every result, accessible labels, keyboard paths and dialog focus. Use data-ui-select for ordinary single-choice filters; preserve their native values/change handlers and resync after programmatic changes. Show sort direction in headings without visible priority digits; explain primary/secondary sorting in advanced controls and accessible names. Empty, loading, disconnected, stale and failed are different states; unavailable telemetry is not zero and is not a successful action. The NGU public dashboard stays read-only. Do not start the bot or call a live mutation endpoint to test layout.

Choose the collection model before adding overflow. Paginated rows flow with the page: retain essential comparison fields and put secondary fields in accessible detail, without removing them from sorting/export. A true matrix may use a named focusable overflow wrapper without pagination. Do not combine pagination with an internally scrolling two-axis table. Use aligned/tabular values and one connected native header band. A visual chart needs readable text for essential values; smaller annotations are a measured local exception, not a precedent for 9px filter labels.

Preserve source datasets and factual copy. Exercise representative populated/empty/extreme states and the existing tests. Use local fixtures for live UI checks where available; identify them as fixtures. Record remaining data or browser limitations in site-theme/docs/VALIDATION.md or the dated successor record.

jehlp-site-qa

Markdown

Review jehlp.net UI changes in the browser for responsive layout, keyboard use, color modes, and regressions across shared-theme consumers.

Read site-theme/docs/QA-MATRIX.md and select the rows relevant to the requested change. Inspect existing test commands before running them; report static tests, script behavior tests, and rendered browser evidence separately.

For shared-theme work, make the browser actually load the candidate local theme. Use temporary response rewriting or request interception for the production theme URL, or a throwaway preview copy. Never commit localhost URLs. Rebuild generated documents and the solver export first. Build Jekyll locally; do not mistake archived _site output for the candidate source.

Exercise 390px and 1440px light/dark layouts, keyboard traversal, meaningful focus, 200% text enlargement, and relevant no-JS/print/reduced-motion behavior. Add widths only when a concrete breakpoint defect needs isolation. Test real primary interactions rather than taking only screenshots. Capture representative evidence with viewport, theme and state.

For the MTL contents disclosure, check hidden links, Escape, heading selection, resize and no-JS. For data dialogs, check naming, focus and close. For solver export, disable network. For the dashboard, preserve read-only behavior and truthful offline/stale state.

For select changes, exercise keyboard/typeahead, Escape without selection, reset, disabled options, dynamic option population, programmatic value synchronization and native fallback. Compare equal-role reader controls for matching size; check that chapter groups survive and redundant glossary controls do not return. Check PNG masthead loading at its actual small size in both modes. Review the first useful viewport for empty hero space or unexplained number gutters. A paginated table must not also need internal two-axis scrolling; inspect first/last rows, details and sort direction. For a true matrix, test connected headers in each scroll direction. For puzzle dividers, inspect the complete rules/examples and the main puzzle's lead-in, solve links and grids on both sides of the boundary. An ornament before the first image is not sufficient: examples stay above, while the complete main puzzle unit stays below. Check the reviewed lead-in/paired-grid exceptions in docs/COMPONENTS.md and verify exact source text, link and diagram preservation; image counts alone cannot establish a correct semantic boundary.

For puzzle sheets, verify a distinct transition ornament, one top edge, and the complete main unit inside the frame, including paired grids and reference charts. Only a verified leading solver-only run may become an action row; post-grid links stay in source order. Check narrow/enlarged-text control wrapping, unchanged bitmap colors and proportions, and print's normal top border without the ornament.

For code listings, check token contrast in both modes and print, keyboard focus and scrolling in a long listing, the first open of a lazily loaded listing and its no-script source link.

Fix demonstrated failures at the responsible layer. Stop optional testing when concrete risks are covered. Leave an honest checklist of unavailable gates; never treat a DOM stub or source regex as proof of browser accessibility.
